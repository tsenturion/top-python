# Практическое задание

## Тема

Порождающие, структурные и поведенческие паттерны проектирования в Python

---

# Цель

Разработать консольное приложение с многослойной архитектурой для управления задачами внутри небольшой компании.

В ходе выполнения задания необходимо спроектировать код таким образом, чтобы архитектура была расширяемой, слабосвязанной и поддерживаемой. Для решения задачи требуется самостоятельно определить, какие порождающие, структурные и поведенческие паттерны будут полезны в различных частях системы.

Основной акцент делается не на количестве функций, а на качестве архитектурных решений, разделении ответственности между компонентами и возможности дальнейшего развития проекта без масштабной переработки существующего кода.

---

# Описание проекта

Необходимо создать консольную систему управления задачами сотрудников.

Приложение должно позволять:

- создавать задачи;
- назначать задачи сотрудникам;
- изменять статусы задач;
- просматривать список задач;
- фильтровать задачи;
- сохранять историю действий;
- выводить различные отчеты;
- поддерживать несколько способов хранения данных.

Система должна быть спроектирована таким образом, чтобы в будущем можно было без значительных изменений добавить:

- новый источник данных;
- новые типы отчетов;
- новые способы уведомлений;
- новые виды задач;
- новые сценарии взаимодействия пользователей.

---

# Задание (шаги)

## Шаг 1. Спроектировать структуру проекта

Создайте отдельные модули для:

- моделей предметной области;
- работы с хранилищем данных;
- бизнес-логики;
- обработки пользовательских команд;
- формирования отчетов;
- уведомлений;
- логирования событий.

Пример структуры:

```text
project/
│
├── main.py
├── models/
├── services/
├── repositories/
├── reports/
├── notifications/
├── commands/
├── storage/
├── logs/
└── utils/
```

---

## Шаг 2. Реализовать предметную область

Создайте сущности:

```python
Employee
Task
Project
```

Для каждой сущности предусмотрите:

- уникальный идентификатор;
- набор атрибутов;
- методы представления объекта;
- проверки корректности данных.

Пример полей задачи:

```python
id
title
description
status
priority
created_at
assigned_employee
```

---

## Шаг 3. Реализовать создание объектов

Система должна поддерживать создание различных типов задач.

Например:

- обычная задача;
- срочная задача;
- задача с дедлайном;
- задача на согласование.

Логика создания объектов должна быть вынесена из клиентского кода.

Код интерфейса не должен напрямую создавать экземпляры всех классов через вызов конструкторов.

---

## Шаг 4. Реализовать работу с хранилищами

Система должна поддерживать несколько вариантов хранения данных.

Например:

```text
Память приложения
JSON-файл
SQLite
```

Пользователь должен иметь возможность переключать способ хранения без изменения остального кода приложения.

---

## Шаг 5. Реализовать слой бизнес-логики

Создайте сервисы:

```python
TaskService
EmployeeService
ProjectService
```

Сервисы должны выполнять:

- создание объектов;
- поиск;
- удаление;
- изменение данных;
- валидацию операций.

Вся бизнес-логика должна находиться именно в сервисах.

---

## Шаг 6. Реализовать систему команд

Консольное приложение должно поддерживать команды:

```text
create_task
create_employee
assign_task
change_status
show_tasks
show_employees
generate_report
exit
```

Добавление новой команды не должно требовать изменения большого количества существующего кода.

---

## Шаг 7. Реализовать уведомления

При изменении состояния задачи должны формироваться уведомления.

Например:

```text
Задача назначена сотруднику
Статус изменен
Задача завершена
Дедлайн истекает
```

Система должна позволять подключать новые способы уведомлений.

Например:

```text
Консоль
Файл
Email (заглушка)
```

---

## Шаг 8. Реализовать историю действий

Необходимо сохранять события:

```text
Создание задачи
Удаление задачи
Назначение сотрудника
Изменение статуса
Создание отчета
```

История должна использоваться для последующего анализа работы системы.

---

## Шаг 9. Реализовать отчеты

Создайте минимум три вида отчетов:

```text
По задачам
По сотрудникам
По проектам
```

Каждый отчет должен формироваться независимо от остальных.

Возможность добавления нового типа отчета должна требовать минимальных изменений в существующем коде.

---

## Шаг 10. Реализовать пользовательский интерфейс

После запуска приложение должно выводить меню:

```text
1. Создать задачу
2. Создать сотрудника
3. Назначить задачу
4. Изменить статус
5. Показать задачи
6. Сформировать отчет
7. История действий
0. Выход
```

Приложение должно работать в цикле до завершения пользователем.

# Подсказки по ключевым частям

## Проектируйте через абстракции

Старайтесь, чтобы бизнес-логика зависела от интерфейсов, а не от конкретных реализаций.

Плохой вариант:

```python
service = JsonRepository()
```

Лучший вариант:

```python
service = repository
```

где конкретная реализация передается извне.

---

## Изолируйте создание объектов

Создание сложных объектов желательно вынести в отдельный слой.

Это позволит:

- скрыть детали создания;
- централизовать валидацию;
- легко добавлять новые типы сущностей.

---

## Разделяйте ответственность

Избегайте ситуаций, когда один класс одновременно:

- хранит данные;
- работает с файлами;
- выполняет бизнес-логику;
- взаимодействует с пользователем.

Каждая часть системы должна отвечать только за свою задачу.

---

## Предусмотрите расширяемость

Представьте, что через месяц заказчик попросит:

- новый формат хранения;
- новый тип уведомления;
- новый отчет;
- новый тип задачи.

Архитектура должна позволять добавлять такие возможности без переписывания существующих модулей.

---

## Минимизируйте связанность

Изменение одного модуля не должно приводить к каскадным изменениям по всему проекту.

Если после добавления новой функциональности приходится менять множество файлов, архитектура требует доработки.
